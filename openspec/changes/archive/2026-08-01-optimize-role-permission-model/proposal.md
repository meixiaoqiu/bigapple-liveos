## Why

当前 Live OS 将成员存在、成员资格、参与状态、议事职责和维护职责都表示为可并列持有的 `RoleAssignment`，并把部分相互独立的职责误建模为上下级角色，导致重复任命、权限来源不清和界面标签混乱。OpenFGA 已作为运行时授权边界，但现有模型仍主要投影 Django 的角色—权限绑定，尚未明确表达任期、专业资格交集以及“议事者”和“维护者”相互独立的授权关系，因此需要在继续扩展治理功能前统一梳理。

## What Changes

- 建立成员状态、资格、角色、任命、权限与 Django 管理标志的权威分类，区分成员记录、派生状态、成员资格、义务职务、专业资格、维护职责、技术后台访问及具体业务权限。
- “观察者”不再作为角色；未注册用户只是在访问公开内容时实施观察行为。
- “贡献者”作为已注册但尚未成为正式成员的派生状态展示，不再创建独立角色任命。
- 将“治理成员”更名为“议事者”。任何当前有效的正式成员均可主动申请成为议事者，申请无需审核；议事者是一项有参与义务的职务，而不是奖励或权限等级。
- 议事者每届任期暂定一年，到期自动失效且不得自动续任；续任必须由本人再次主动申请并产生新的任期事实。
- 将“治理管理员”更名为“维护者”。维护者负责明确授予的维护与管理操作，但不因维护者身份自动获得议事、发表正式意见或投票的权利。
- 议事者与维护者属于相互独立的职责维度，不构成上下级或能力包含关系；同一成员可分别持有二者，也可只持有其中之一。
- 普通提案的选民范围由当前有效的正式成员资格与议事者任期共同确定；专业提案还必须同时具备对应专业资格。系统不创建“财务投票者”“建设投票者”等角色组合。
- 专业资格作为独立、可审计的资格事实参与授权；面试、评估和资格认定过程由系统外制度完成，本变更只消费已经确认的资格结果。
- 专业资格的录入与撤销属于维护操作，必须由具有明确专业资格维护能力的维护者执行；普通成员不得凭可用状态写入或撤销该权威事实。
- 规定只有当前真实生效、需要独立授权判断的资格或职务才写入权威记录；由状态、资格交集或授权策略推导出的标签和能力不得通过重复角色任命表达。
- 将 OpenFGA 模型从单纯角色权限投影扩展为可表达正式成员资格、议事者有效任期、提案专业范围、专业资格、维护者独立权限及 world 隔离的授权模型；业务入口继续只通过 `AuthorizationService` 检查具体权限并保持失败关闭。
- 禁止按具体个人身份创建专属角色或授权例外。初始化与日常管理所需能力必须来自可复用、可审计并能按同一治理规则授予其他合格成员的普通角色与权限；Django `is_staff`、`is_superuser` 只控制技术后台，不产生业务身份。
- 统一角色展示规则：授权事实、有效权限和面向用户的身份分离；同一职责族不重复显示推导标签，不同职责维度分别展示。成员同时担任议事者和维护者时，详情必须同时显示二者，不能以所谓“最高角色”隐藏其中一项。
- 以未上线系统的干净基线实施重构：删除旧角色、旧任命、旧权限绑定、旧提案选民范围、旧 OpenFGA tuple 与旧显示逻辑，不保留兼容层、旧名称别名或数据回滚路径。旧制度名称与清理过程只保留在 OpenSpec 文档中。
- 旧提案选民范围不得在 schema 迁移时被静默解释为新选民政策；遇到遗留提案数据时迁移必须失败并要求重置到干净基线。
- 规范角色必须同时属于唯一的角色目录组织并匹配目录定义；同名的其他组织角色不得触发正式成员资格、凭证或其他内置角色规则。
- 增加角色与权限矩阵、议事者申请与任期、任期到期后重新申请、普通和专业提案选民范围、维护者无自动投票权、资格撤销与到期、用户停用、OpenFGA 不可用和跨 world 隔离的回归验证。
- **BREAKING**：依赖“治理管理员包含治理成员能力”“维护职责自动产生投票权”“成员同时具有所有下级 active 角色”或直接按角色名称授权和展示的内部代码与测试，将改为使用规范化事实或具体权限判断；现有角色相关测试与仿真数据必须重建，公开 API 如需改变 payload，必须先单独更新对应 technical contract。

## 目标与非目标

### 目标

- 让角色名称表达真实职责，使“议事者”和“维护者”不再暗示身份高低。
- 让普通提案和专业提案的投票资格可以由 OpenFGA 从当前事实稳定推导。
- 让议事者的一年任期、主动加入和不自动续任成为可验证的系统规则。
- 让角色展示准确表达成员当前承担的独立职责，而不列出重复或虚构的下级角色。

### 非目标

- 本变更不实现专业资格的面试、评估、培训或认定流程，只记录或消费系统外已经确认的资格结果。
- 本变更不实现议事缺席的扣分金额、通知有效性、豁免、申诉和撤销机制；这些规则需要单独的治理变更。
- 本变更不把所有成员资格、职责和专业资格压缩成一条全局等级链。
- 本变更不为任何具体个人创建专属角色或业务授权例外。
- 本变更不保留未上线旧制度的数据库记录、代码兼容分支、显示名称或 OpenFGA 关系；过程文档是唯一保留旧制度信息的位置。

## Capabilities

### New Capabilities

- `role-authority-facts`: 定义成员资格、派生参与状态、议事者任期、维护者职责、专业资格、直接事实规则、个人专属角色禁令与上线前清理不变量。
- `openfga-authorization-policy`: 定义 OpenFGA 中议事者、维护者和专业资格的独立关系，普通与专业提案的资格交集，具体权限、失败关闭与 world 隔离。
- `role-presentation`: 定义普通列表、成员详情和维护界面如何从权威事实生成不重复、可解释且不暗示虚假等级的身份展示。

### Modified Capabilities

无；当前仓库尚无已归档的 OpenSpec 主规格。

## Impact

- 主要影响 `core.models.identity`、`core.member_roles`、角色任命服务、专业资格事实、权限服务、`AuthorizationService`、OpenFGA authorization model 与 tuple rebuild/probe 命令。
- 影响注册后的贡献者状态、正式成员准入、议事者申请与任期、维护者任命、bootstrap/seed、提案选民范围、投票与执行、Django Admin、workspace 和 observer 成员资料中的角色读取与显示。
- 需要数据库 schema 迁移和明确的开发／仿真数据重置入口；旧角色相关数据允许且必须清理，不得作为新制度的兼容输入。
- 需要同步 `bigapple-docs` 中治理边界、架构、数据库结构、Admin、Observer、产品角色和相关 technical contracts（仅在公开 API/schema/payload 实际变化时）。
- 不新增第三方依赖；不以 Django `is_staff`/`is_superuser` 替代业务授权。
