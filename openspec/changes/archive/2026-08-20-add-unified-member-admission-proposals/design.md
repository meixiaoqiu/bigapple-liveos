## Context

详见 `proposal.md`。当前 `ApprovalProposal` / `ApprovalDecision` 已承载采购等审批，但它仍依赖硬编码审批角色组，缺少版本化选民规则、快照、截止、通用票数计算和可扩展业务执行适配器。成员准入已在服务层失败关闭；旧 `Proposal` 体系不得恢复。项目尚未上线，可直接调整干净迁移基线，不承担旧提案数据兼容责任。

## Goals / Non-Goals

**Goals:**

- 让 `ApprovalProposal` 成为唯一的跨业务提案聚合根，不新建第三套平行提案系统。
- 将通用生命周期、选民规则、投票、结果和执行从具体业务中分离。
- 通过成员准入适配器证明一个业务可以接入统一核心且不绕过角色任命服务。
- 让规则新增角色引用时只更新权威目录和规则数据，不修改提案核心分支。
- 保持 OpenFGA 授权、事务一致性、幂等、实名审计及 real/simulation 隔离。

**Non-Goals:**

- 不在本批重写现有采购审批的业务规则，也不把采购审批宣称为已经完成新选民规则迁移。
- 不允许动态执行代码、原始查询或任意 JSON 表达式。
- 不在本批开放其他已登记的失败关闭流程。
- 不保留旧 `Proposal` 表或兼容入口。

## Decisions

### 1. 演进现有 `ApprovalProposal`，不新增平行聚合根

在 `core.models.approval_workflow` 内扩展 `ApprovalProposal` 的状态、规则引用、截止、结果和执行字段，并新增规则版本、选民快照、票据修订及执行记录模型。现有采购类型继续通过同一聚合根运行，但在各自迁移完成前仍使用明确标记的审批策略适配器。

选择该方案是因为产品目标是所有需要共同决定的流程最终只有一个承载位置。另建 `GovernanceProposal` 会让 `ApprovalProposal` 与新模型长期并存，重复列表、审计、权限和执行入口。

未采用方案：恢复已删除的旧 `Proposal`；这会破坏长期退役规格和残余检查。未采用方案：一次性重写采购、角色、财务与仿真全部流程；范围过大，无法独立证明成员准入闭环。

### 2. 状态机与业务动作分层

统一服务只负责状态机、规则冻结、快照、票据、结果计算和执行编排。具体动作通过受控的提案类型适配器登记，适配器必须声明：来源对象类型、幂等键、发起权限、执行权限、执行前置条件及领域服务调用。

成员准入适配器引用 `MemberApplication`，执行时调用既有角色任命服务创建一年期守约者任期并更新报名结果。适配器不得直接创建 `RoleAssignment`，不得附带执衡者、管理员或财务职责。

未采用方案：在 `execute_proposal()` 中持续增加 `if proposal_type == ...` 分支。该方式会让统一服务重新变成各业务规则的集中大杂烩。

### 3. 规则模板可编辑，已发布版本不可变

规则由模板、不可变发布版本和受验证的选择器配置组成。选择器仅允许稳定类型，例如角色代码、派生参与状态、专业资格代码、明确排除关系及 `ALL` / `ANY` 组合。发布规则需要新增的具体权限 `governance.manage_proposal_policies`，不能用 Django `is_staff` 或页面可见性替代。

提案开始表决时引用一个已发布版本，复制阈值、截止和未决处理参数，并生成逐成员快照。之后修改模板只影响新提案。

未采用方案：把所有规则字段直接放在提案 `metadata`。这样难以验证、索引、版本化和审计。未采用方案：为每个角色增加布尔字段；新增角色会要求迁移和核心代码修改。

### 4. 准入政策不设置隐藏业务默认值

首个有效成员准入政策必须由有权管理员在 workspace 配置并发布，明确选民角色集合、通过与拒绝阈值、最低参与、期限和未决处理。没有政策时允许保存报名，但提案保持不可表决状态并显示配置缺口。

测试和 simulation seed 使用显式测试政策，不把测试数值变成 real world 制度默认值。这样无需在本次规划中替产品负责人猜测准入选民与阈值，且上线前能够通过配置完成最终决定。

未采用方案：默认由管理员单人决定；这会退化为后台审核。未采用方案：默认所有执衡者简单多数；用户尚未确认该制度，不能把假设固化为权威规则。

### 5. 票据采用只追加修订与单一有效投影

每次投票或改票都追加不可变票据修订，另以序号或明确的当前标记确定该成员最后一票。结果计算只读取快照内、当前仍合格成员的最后有效选择，同时保留历史修订用于审计。

该设计兼顾截止前改票与事后追溯。数据库约束和事务锁保证同一提案、成员、修订序号唯一，避免并发双写产生两个当前选择。

未采用方案：覆盖同一行；它会丢失实名决策历史。未采用方案：完全禁止改票；当前产品没有这一制度要求，不必引入额外限制。

### 6. 判定与执行分离并记录幂等结果

判定器仅根据冻结参数产生已通过、已拒绝或已过期结果，并保存输入计数和规则版本。执行器只有在提案已通过、执行者通过 OpenFGA 具体权限检查、来源对象仍满足前置条件时才调用适配器。

执行记录包含执行者、开始与完成时间、结果、可公开错误码和幂等键。领域动作与提案状态在同一 world 数据库事务中完成；重复执行返回已有结果。

未采用方案：通过即由投最后一票的人自动执行。投票权不等于执行权，且自动副作用不利于故障恢复和实名责任追踪。

### 7. 页面与服务共用解释结果

领域层返回结构化资格结果，包括是否允许、拒绝代码、使用的规则版本和可公开说明。workspace 用同一结果决定按钮与提示；所有 POST 仍在服务层重新授权。申请人、选民和执行者看到的内容不同，但来源是同一权威状态，不复制三套判断逻辑。

未采用方案：仅在模板隐藏按钮；内部服务、Admin 或命令仍可能绕过。

### 8. World 路由和 OpenFGA 按现有边界执行

所有统一提案模型属于 world 数据库；服务从可信 request/world context 或显式数据库 alias 获取 world，不接受表单自选 world。OpenFGA tuple 与检查使用该 world 对应 store/model。测试默认使用隔离设置，另增加 real/simulation 多库边界测试。

## Risks / Trade-offs

- [现有 `ApprovalProposal` 同时承载旧式审批策略和新式选民策略] → 用明确策略类型与适配器注册表隔离，禁止成员准入回退到硬编码角色组，并将其他类型逐项列入后续迁移。
- [规则配置过于灵活导致操纵选民] → 只允许制度许可模板、稳定目录选择器和不可变发布版本；禁止提案发起者临时拼装私有规则。
- [快照与实时资格结果不同] → 快照用于固定候选范围，投票时再验证当前资格；审计同时保存两种事实及拒绝原因。
- [结果已通过但领域动作失败] → 判定与执行分离，记录执行失败且允许有权人员在修复前置条件后幂等重试，不回滚实名投票结果。
- [规则、投票与事件写入不一致] → 在同一 world 数据库事务中加行锁处理，并测试异常回滚后没有部分权威状态。
- [文档再次把其他提案写成已开放] → 更新迁移矩阵并扩展旧残余/能力一致性检查，只将成员准入标记为本批恢复。

## Migration Plan

1. 先更新 sibling Docs 技术契约，定义统一提案、规则版本、快照、票据和执行 payload。
2. 在干净迁移基线中扩展 `ApprovalProposal` 并新增相关模型、约束和索引；不迁移旧提案数据。
3. 实现通用状态机、规则发布与评估、快照、投票、判定和执行编排，保持成员准入入口关闭。
4. 实现成员准入适配器、政策配置和 workspace 页面，补齐服务层授权与审计。
5. 在隔离测试数据库和 simulation 明确测试政策下完成闭环，验证 real/simulation 隔离与其他未迁移流程继续关闭。
6. 更新 OpenFGA 模型和 tuple，重建 real/sim 模型后运行探针；人工核对 `.env` 中对应 model id。
7. 自动化和人工验收通过后，仅开放成员准入入口。

回滚时回退代码与迁移并重置未上线 world 数据库及对应 OpenFGA store/model。不得恢复旧 `Proposal` 结构或将新提案数据转换回旧模型。
