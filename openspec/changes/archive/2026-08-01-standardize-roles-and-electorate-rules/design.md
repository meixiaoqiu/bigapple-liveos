## Context

变更动机见 `proposal.md`，行为契约见四份 delta spec。当前 `Proposal.ElectoratePolicy` 只支持 `general_deliberation` 和 `professional_deliberation`，选民计算通过专用分支直接查询正式成员、议事者与专业资格。OpenFGA 使用固定 `formal_member`、`deliberator`、`maintainer` relation，而提案保存选民快照并在投票时重新检查当前资格。

项目未上线，可重置仿真 world，因此本设计不保留旧命名、旧选民政策或旧 OpenFGA relation 的兼容层。真实 world 仍必须失败关闭：若存在无法无损解释的旧提案数据，schema 迁移必须阻止而不得静默改写其治理语义。

## Goals / Non-Goals

**Goals:**

- 建立中文正式命名与英文语义标识的唯一目录，同步 Django、OpenFGA、页面、测试与文档。
- 以可版本化规则模板、结构化条件树和通用评估器替换固定选民政策分支。
- 保留 Django 权威事实、选民快照审计和 OpenFGA 运行时授权三者的分工。

**Non-Goals:**

- 不允许用户编写任意表达式、SQL、Python 或 OpenFGA DSL。
- 不将贡献者变为直接角色，不将专业资格变为组合角色。
- 不在本变更实现新的角色授予流程、专业认定流程或执衡义务处罚。

## Decisions

### 1. 正式命名使用单一权威目录

角色目录中的三个直接事实改为 `Covenanter`、`Deliberator`、`Maintainer`，中文显示分别为守约者、执衡者、典守者。`Contributor` 作为目录中的派生状态定义，由注册、User/Member 可用和缺少当前 Covenanter 资格推导。

备选方案：只改中文显示名称，保留 `formal_member` 等旧代码语义。未采用，因为用户明确要求英文也是代码的正式语义表达，保留旧语义会持续制造中英文分岔。

### 2. 选民规则使用版本化模板与提案快照

新增选民规则模板和版本化定义。模板包含稳定 code、中文名称、状态、版本和结构化条件树；提案保存模板版本引用及已规范化条件快照，使后续模板修改不会改写旧提案语义。

备选方案：提案只保存模板外键并始终读最新模板。未采用，因为模板修改会静默改变已创建提案的选民和治理语义。

### 3. 条件树只支持封闭选择器集合

条件节点使用 `ALL`、`ANY`、`NOT` 组合，叶节点使用稳定选择器类型和对象引用。首批选择器为 `registered_member`、`derived_status`、`catalog_role`、`professional_qualification`；后续可通过统一注册表增加经审查的新选择器，但提案流程本身不增加新分支。

备选方案：保存任意 JSONLogic 或 Python 表达式。未采用，因为难以限制访问范围、审计、稳定版本并证明不存在选民操纵或代码执行风险。

### 4. 提案类型约束规则模板

提案类型与可用选民规则模板之间建立显式允许关系，必要时再增加不可删除的最低条件。发起人只能选择允许模板和模板开放的参数，不能提交原始条件树。

首批模板为：

| 模板 | 必要语义 |
| --- | --- |
| 社区共议 | 有效注册成员，贡献者、守约者、典守者或执衡者可被包含。 |
| 守约事务 | 当前有效守约者资格 AND 当前有效执衡者任期。 |
| 专业事务 | 守约事务条件 AND 一个明确专业领域的当前有效资格。 |
| 典守事务 | 当前有效典守者职责，仅用于制度明确允许典守者决定的操作性事项。 |

### 5. Django 计算选民，OpenFGA 检查提案对象能力

Django 保存角色、资格、状态、规则模板和提案条件快照，通用评估器生成选民快照并在投票时重新计算。OpenFGA 保留对应 world 内成员对具体 proposal 的 `can_vote` 授权边界，但不为每个规则模板增加专用 relation。

备选方案：将任意条件树完整翻译为 OpenFGA 模型。未采用，因为 OpenFGA relation 是模型级定义，动态条件会要求频繁发布新模型，也难以表达当前 Django 中的时间和派生状态。

### 6. 迁移以干净基线为准并保护真实 world

schema 迁移创建新规则结构并删除旧选民政策字段。如任何数据库存在旧提案数据或旧规范角色事实，迁移或专用预检必须阻止并要求明确重置，不得自动猜测新规则。simulation world 通过重置命令建立新基线；real world 不得被脚本自动清理。

## Risks / Trade-offs

- [规则结构过度灵活变成选民操纵工具] → 选择器集合封闭，提案类型约束模板，发起人不接触原始条件树。
- [规则评估在大量成员上产生过多查询] → 各选择器返回可组合 QuerySet 或成员 ID 集，快照生成使用集合查询，不按成员逐个执行规则。
- [旧提案数据无法无损映射] → 未上线阶段发现旧数据即失败，使用明确 simulation reset 重建，不静默转换。
- [命名迁移遗漏导致同一事实有两个标识] → 全仓静态检查旧名称、角色目录唯一校验、OpenFGA 模型版本与干净基线矩阵共同阻止混用。
- [Django 与 OpenFGA 结果分歧] → 授权服务保留对具体 proposal 的探针、失败关闭和双边验收矩阵。

## Migration Plan

1. 盘点代码、数据库、OpenFGA、测试、契约和文档中的四种正式名称及所有旧名称。
2. 先更新必要的 technical contracts，再实施角色目录、schema 与提案选民规则模型。
3. 实现通用规则验证器、QuerySet 选择器、快照生成和投票重检，然后替换旧提案政策分支。
4. 发布新 OpenFGA 模型，重建 simulation world 与 tuple，不保留旧 relation。
5. 更新页面、管理输出、中英文文档与验收矩阵，执行全仓旧名称检查。
6. 运行角色、规则、提案、OpenFGA、world 隔离、界面和完整 Docker 回归；通过后同步主规格并归档。

未上线无数据回滚要求；如开发期需要回退代码，应同时重置对应 simulation world 和 OpenFGA store/model，不尝试在新旧规则之间自动反向转换。
