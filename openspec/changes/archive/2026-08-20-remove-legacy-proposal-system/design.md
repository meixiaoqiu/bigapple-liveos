## Context

详见 `proposal.md`。当前旧 `Proposal` 是带选民快照、阈值、投票和执行的治理系统；新 `ApprovalProposal` 当前主要是审批决策记录，尚未完整承接旧系统能力。旧 UI 和部分 URL 曾被提前移除，但旧权威模型仍被成员准入、角色任命、财务职责、反馈、仿真、观察页面和命令使用。项目未上线，用户已明确不保留任何旧 world 数据，只在 OpenSpec 与 Git 中保留过程历史。

## Goals / Non-Goals

**Goals:**

- 让旧提案系统在模型、迁移、代码、页面、测试、文档和契约中均不存在。
- 用机械检查证明不存在运行时兼容或回退路径。
- 把删除后暴露的每个业务缺口转成结构化迁移清单。
- 保证未迁移入口面向用户失败关闭，面向开发者明确失败。

**Non-Goals:**

- 不在本变更中增强 `ApprovalProposal`。
- 不用临时适配器把旧模型包装成新模型。
- 不迁移旧数据，也不保持旧 API 兼容。
- 不以“让完整回归暂时全绿”为理由保留旧代码。

## Decisions

### 1. 采用硬删除，不采用双写或渐进兼容

旧系统的模型、字段和服务将直接删除，所有引用必须编译失败、导入失败、Django check 失败或测试失败，直到被显式处理。由于项目未上线且 world 可重置，双写只会延长不确定性。

未采用方案：保留只读兼容层。该方案仍会让残余业务看似正常，违背本次变更目的。

### 2. 制度规格与旧实现分离

`configurable-electorate-rules` 等规格继续保留，作为新统一提案系统必须满足的长期要求。只删除实现，不删除成员准入投票、角色任命表决、专业资格限制、阈值和审计等业务语义。

未采用方案：随代码一起删除旧业务测试和规格。该方案会让后续统一系统无法判断需要恢复什么。

### 3. 用残余清单驱动删除

先生成机器可读的旧标识目录，至少包括模型名、字段名、表名、模块、URL 名称和 contract 字段。每轮删除后运行扫描；扫描只允许 OpenSpec 过程文档和明确的禁止名单本身出现旧标识。

未采用方案：只使用全文搜索人工判断。全文搜索容易漏掉字符串构造、迁移定义、反向关系和文档契约。

### 4. 未迁移用户入口使用统一关闭状态

仍需保留的报名、角色任命或其他页面可以继续展示非提案信息，但涉及提案决策的写操作必须关闭，并使用统一说明。关闭页面不得导入旧模型，也不得直接改写最终状态。

未采用方案：允许页面返回 500。开发检查需要高声失败，但面向用户的请求必须可理解、可恢复。

### 5. 重建干净迁移基线

由于不保留旧数据库和历史迁移残余，实施时重建受影响 app 的干净迁移基线，使从空数据库安装时从未创建旧表或字段。启动脚本应检测旧结构并提示重置，而不是编写数据转换迁移。

未采用方案：追加 `DropModel` 迁移。它可以删除运行时表，但旧模型定义仍永久存在于迁移代码，不符合“过程历史只保留在 OpenSpec/Git”的要求。

### 6. 分四道删除闸门

1. 盘点闸门：冻结旧依赖、制度规则和公开契约清单。
2. 运行时闸门：删除页面、服务、命令和仿真调用，未迁移入口失败关闭。
3. 数据闸门：删除字段、模型、迁移定义并重建空库。
4. 证明闸门：残余扫描、Django check、迁移检查、定向测试、完整回归和 Docs 构建。

每一道闸门完成后才进入下一道，避免同时面对不可分类的大量错误。

## Risks / Trade-offs

- [多个业务流程暂时不可用] → 在迁移清单中逐项登记，并在页面明确关闭；后续按业务优先级迁移到统一系统。
- [删除模型产生大范围导入错误] → 先删除运行时调用和字段引用，再删除模型导出，最后重建迁移基线。
- [直接状态写入绕过提案] → 为需要提案决定的最终状态服务增加失败关闭测试和结构扫描。
- [旧标识与普通英文单词重名导致误报] → 禁止目录使用路径与语义组合，不使用无上下文的 `proposal` 单词全局封禁。
- [重建迁移基线影响其他模型] → 在三个全新隔离数据库上执行迁移、schema 检查和完整回归，并记录需要用户重置的开发 world。
- [文档暂时描述不可用功能] → 同步标记当前实现状态，但保留中远期统一提案制度目标。

## Migration Plan

1. 生成旧系统依赖清单，并按“旧系统专属”“需新系统承接的业务语义”“名称相同但属于新系统”分类。
2. 冻结统一关闭文案和迁移缺口文档，先修改用户入口、命令、仿真和 seed，使其不再调用旧系统。
3. 删除旧领域模块、Admin、信号、事件投影、API、URL、模板分支和测试辅助函数。
4. 删除所有旧外键和反向关系，调整受影响模型，使未迁移业务不再保存旧提案引用。
5. 删除旧模型与导出，清理 OpenFGA、事件、观察台和仿真残余。
6. 重建干净迁移基线；使用全新 control、real、simulation 测试数据库验证 schema。
7. 更新 technical contracts、Docs、OpenSpec 主规格和残余禁止检查。
8. 运行定向及完整验证，输出统一提案系统待迁移清单。

回滚策略：不提供运行时旧系统回滚。实施过程通过 Git 分阶段提交保留代码级恢复点；一旦干净迁移基线确定，现有开发数据库必须重置。
