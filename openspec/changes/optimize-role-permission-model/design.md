## 背景

变更动机见 `proposal.md`，必须实现的行为见三份能力规格。

当前授权路径为 `Member -> active RoleAssignment -> RolePermission -> Permission`，运行时统一经过 `AuthorizationService`；选择 OpenFGA 后端时必须失败关闭。`RoleAssignment` 已有 `start_at`、`end_at`、状态和来源字段，适合表达有固定期限的职责。当前 `Proposal` 的选民范围由旧角色或组织字段表达，不能表示专业资格交集。

项目尚未上线，仿真 world 可以频繁重置。因此不设计旧制度的兼容层、数据迁移、旧名称别名、旧事件时间线或回滚到旧模型。旧制度的信息只保留在本次 OpenSpec 过程文档中。

## 目标 / 非目标

**目标：**

- 建立成员资格、派生状态、议事职责、维护职责和专业资格的单一新制度基线。
- 复用 `RoleAssignment` 表达正式成员、议事者和维护者的当前任期或任命。
- 让 OpenFGA 从正式成员资格、有效议事者任期和专业资格交集推导提案投票权，并让维护者只获得明确绑定的维护权限。
- 提供只作用于明确 simulation world 的可重复重置与种子数据装载入口。
- 用同一显示投影在所有界面呈现新制度身份，不显示旧标签。

**非目标：**

- 不实现专业资格的面试、培训、评估、考试或认定流程；系统只保存外部制度已经确认的结果。
- 不实现议事缺席的扣分、通知、豁免、申诉和撤销机制。
- 不支持一项提案同时要求多个专业领域分别表决；该制度需要独立变更。
- 不保留旧角色、旧任命、旧权限绑定、旧选民范围、旧 OpenFGA tuple、旧显示名称或代码兼容分支。
- 不提供旧制度数据迁移或回滚路径，也不新增第三方依赖。

## 决策

### 1. 使用多维目录，不建立角色等级链

新制度目录只包含以下规范概念：

| 规范概念 | 权威表示 | 直接记录 |
| --- | --- | --- |
| 社区主体 | `Member` | 是 |
| 贡献者 | `Member` 加正式成员资格查询 | 否 |
| 正式成员 | `RoleAssignment` | 是 |
| 议事者 | 有一年期限的 `RoleAssignment` | 是 |
| 维护者 | 独立的 `RoleAssignment` 与 `RolePermission` | 是 |
| 财务、建设、运营等资格 | 专业资格权威模型 | 是 |

匿名访问是观察行为，不是身份或角色；正式成员申请是申请状态，不是角色。议事者与维护者是不同职责维度，不互为父子，也不互相推导。目录只在同一维度内抑制重复标签，不能把维护者显示成高于议事者的等级。

备选方案：为所有角色设置 `parent_role` 和数字等级。没有采用，因为专业资格、成员资格和两类职责无法可靠地排成一条高低链。

### 2. 议事者复用 `RoleAssignment` 的一年任期

议事者申请服务仅接受当前有效正式成员，使用新的 `SELF_APPLICATION` 来源记录本人主动申请，并创建一条 `start_at` 到 `end_at` 的任期。服务拒绝重叠的 active 任期，不修改当前任期来模拟续任。

结束时间按成员所在 world 的本地日历计算为开始时间的一周年；开始日为 2 月 29 日时，下一年使用 2 月最后一日。运行时统一有效性查询以 `status=active`、`start_at <= 当前时间 < end_at` 为准，不需要定时任务使到期任期失效。到期后的再次申请创建新任期，不延长旧任期。

备选方案：新增专门的议事任期表。没有采用，因为现有 `RoleAssignment` 已具备成员、角色、来源和起止时间字段；单独建表会增加不必要的双重事实来源。

### 3. 维护者保持独立任命与显式维护权限

维护者使用普通任命流程和明确的 `RolePermission`，并要求有效正式成员资格。本变更不改变其具体维护权限的治理授予程序。

维护者任命服务和 bootstrap 不得创建议事者任期，OpenFGA 也不从维护者关系推导投票或正式审议能力。成员想参与议事时，必须主动申请议事者任期。

备选方案：维护者继承议事者能力。没有采用，因为维护职责与无偿议事义务不同，自动继承会错误增加投票权和缺席责任。

### 4. 专业资格使用独立的权威模型

新增专业领域定义和成员专业资格记录，至少包含稳定领域代码、中文名称、成员、状态、确认来源、确认人、开始时间、结束时间和必要的外部证据说明。资格录入服务只接受已由系统外制度确认的结果；它不实现面试或评估工作流。

专业资格的有效性由状态和起止时间共同决定。它可以按受众展示，但与 `CredentialGrant` 分离；证书、勋章和其他公开凭证不参与授权。

专业资格的录入与撤销使用明确的 `governance.manage_professional_qualifications` 维护能力。服务层在写入前通过统一授权边界校验操作成员；仅“成员和账号可用”不是写入资格事实的充分条件。该能力随通用维护者职责投影到 OpenFGA，避免由页面或未来调用方自行承担权限校验。

备选方案：把专业资格写成“财务投票者”等组合角色，或让 `CredentialGrant` 直接参与授权。前者会随领域和职责组合膨胀，后者违反现有凭证边界，均不采用。

### 5. 提案使用服务端选民政策

新提案使用服务端验证的选民政策：普通议事提案使用议事者，专业议事提案使用议事者加一个明确的专业领域。专业领域必须引用已启用的领域定义，未分类或无效的专业提案失败关闭，不得回退为普通提案。

开始表决时，选民快照由当前有效的正式成员资格、议事者任期和可选专业资格交集生成。投票操作仍通过 `AuthorizationService` 重新验证当前资格；快照不得旁路当前授权。新提案不读取旧角色或组织选民范围，提案人不能自行选择角色或省略专业领域绕过资格要求。

备选方案：继续让每项提案自由选择任意角色作为选民范围。没有采用，因为它不能表达专业资格交集，也允许不一致的资格规则。

### 6. Django 保存当前事实，OpenFGA 推导能力

Django 是当前成员资格、任期、维护任命和专业资格的权威来源。OpenFGA 只接收当前有效的最小直接关系，并推导：

- `can_vote_general`：正式成员资格与议事者任期的交集；
- `can_vote_professional`：正式成员资格、议事者任期和所需专业资格的交集；
- 维护者明确绑定的 `can_*` 维护权限；
- 既有对象级权限和 world 隔离。

贡献者、匿名观察、已到期任期、组合投票者和展示标签不得投影为 tuple。业务入口检查具体 `can_*` 能力；只有提案选民范围等当前业务事实需要时才查询角色事实。

备选方案：将所有关系和显示元数据只保存在 OpenFGA。没有采用，因为 OpenFGA 不能提供成员任期、资格来源和提案选民范围的权威数据。

### 7. 显示服务按维度生成当前身份摘要

只读显示服务返回派生状态、成员资格、议事职责、维护职责、专业资格和当前限制原因。公开列表可按空间显示简短身份摘要，但成员详情必须同时显示有效的议事者和维护者职责，不得因为其中一项看似更高而隐藏另一项。

界面不显示观察者、预备成员、大苹果成员、治理成员、治理管理员或任何旧制度标签。新制度测试数据从干净基线产生，不提供旧名称转换或历史时间线。

### 8. 使用可重复的仿真 world 重置建立基线

实现显式选择 simulation world 的重置与种子装载路径。重置清除该 world 的角色、任命、权限绑定、提案选民数据、专业资格试验数据和 OpenFGA tuple，然后只装载新目录定义的最小可用数据。重置不得读取、写入或删除其他 world。

代码删除旧角色常量、旧名称显示、旧选民范围分支和旧授权关系，而不是保留兼容别名。授权矩阵只验证新制度结果；不再比较或加载旧模型。

### 9. 公开契约变化必须单独设门槛

本变更可能增加提案选民政策、专业领域或身份展示字段。实施前必须盘点公开 API payload；一旦涉及 schema 或 payload，先更新并审核 `bigapple-docs/static/technical-contracts/` 中的对应契约，再实施 Live OS 代码。

### 10. 规范角色以唯一目录组织和目录定义共同识别

角色目录组织名称在数据库中受条件唯一约束保护。角色任命服务仅在角色属于该唯一组织、名称匹配目录定义时，才应用内置角色的正式成员前置条件或签发正式成员编号凭证。其他组织即使使用相同显示名称，也不能伪装为规范角色；服务拒绝这种保留名称的任命，而不是产生一条无法被运行时权限识别的事实。

备选方案：仅按角色显示名称匹配。没有采用，因为 `Role.name` 只在组织内唯一，跨组织同名会使凭证事实与授权事实分叉。

### 11. 遗留提案数据必须阻止 schema 迁移

项目未上线且旧制度数据不需要保留，但迁移不能把旧的按角色、组织或全体成员范围悄悄改写为普通议事。迁移在删除旧选民范围字段前检查是否存在遗留提案；若存在则失败并要求从干净数据库或显式重置基线重新开始。这样保留“旧数据不进入新制度”的决定，同时避免伪造新制度下的治理语义。

备选方案：无条件删除所有提案及其依赖记录。没有采用，因为提案被多个权威模型以保护关系引用，迁移不应在未明确列出完整删除范围时扩大破坏半径。

## 风险 / 权衡

- [重置范围错误] → 重置命令要求明确的 simulation world 标识，并测试其他 world 完全不变。
- [专业资格模型与既有凭证概念相近] → 明确分离数据模型、服务和授权路径，避免证书或勋章意外获得权限。
- [一届任期到期引发用户困惑] → 在成员详情显示当前职责是否有效和再次主动申请入口，不做隐式续任。
- [新提案字段改变公开接口] → 以 technical contract 作为实现前门槛。
- [旧代码残余放宽权限] → 通过静态检查和新制度授权矩阵阻止旧角色名称或 tuple 进入运行时路径。
- [旧提案被错误重新解释] → schema 迁移遇到遗留提案即失败，要求干净基线。
- [同名动态角色污染规范事实] → 唯一目录组织约束与服务层目录角色判定共同失败关闭。

## 基线建立方案

1. 完成角色目录和新制度权限清单，删除旧角色常量、显示标签与授权分支。
2. 新增议事者自助申请、维护者独立任命、专业资格模型和服务，并执行 schema 迁移。
3. 以服务端选民政策替换旧提案选民范围，更新投票检查和 OpenFGA 模型。
4. 实现仿真 world 重置与新制度种子装载，重建 tuple，并运行角色、选民和授权矩阵。
5. 更新 workspace、observer、Django Admin、文档和必要的 technical contract；完成回归测试后只保留新制度代码与数据基线。
