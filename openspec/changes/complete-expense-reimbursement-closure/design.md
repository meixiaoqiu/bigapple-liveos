## Context

参见 [proposal.md](proposal.md) 的动机。当前代码已有 `ExpenseClaim`、`FinanceReview`、`FinanceTransaction`、`core.finance_services`、workspace 页面和公开财务页；付款动作只记录“现在已付款”，没有付款日期、方式、凭证或执行后端事实。

头像变更已经建立 Magika、Pillow、Django Storage、OCI S3 兼容配置、随机 key、world runtime 前缀、失败补偿和仿真重置清理。不过 `AvatarStorageGateway`、头像 key 和替换删除语义仍是窄边界，不能直接承担永久财务证据。已有附件规格明确要求正式附件使用独立权威模型、真实业务外键和只追加更正版本。

技术契约中目前没有报销公共 API 或 schema。本次首先完成 Django 页面和内部权威模型，不增加公共 API；若实施时发现必须改变 API，则先在 sibling docs 仓库补契约。

## Goals / Non-Goals

**Goals:**

- 复用安全文件处理与 Storage 原语，同时建立和头像生命周期隔离的正式业务附件模型。
- 保证提交报销与附件关联、付款确认与付款凭证关联在失败时不会产生半完成权威状态。
- 让私有原件、公开脱敏副本、附件更正和业务对象权限具有明确模型语义。
- 让内置人工付款成为默认完整后端，并建立足够窄的可替换接口。
- 保持当前模块化单体、world 数据库路由、OpenFGA 权限和统一事件账本边界。

**Non-Goals:**

- 不建立跨所有领域的万能 GenericForeignKey 附件框架。
- 不实现杀毒沙箱、OCR、发票验真、预览渲染或 Office 文档解析。
- 不实现第三方后端、异步同步平台、Webhook 或通用集成总线。
- 不改变仿真快照归档的位置或语义；world 重置仍只清理 runtime。
- 不允许提交后任意编辑报销核心金额、原件或既有审核/付款事实。

## Decisions

### 1. 权威附件模型放在 `core.models.attachments`

新增 `Attachment` 保存稳定业务 ID、对象 key、检测媒体类型、字节数、SHA-256、上传人、受众、生命周期、来源附件和时间。新增带真实外键的 `ExpenseClaimAttachment`，明确用途为支出凭证、付款凭证或公开材料，并关联具体 `ExpenseClaim`；付款凭证还可关联 `PaymentExecution`。

不采用 `GenericForeignKey`，因为它不提供数据库外键完整性，容易绕过业务权限和 world 路由。也不把附件字段直接堆在 `ExpenseClaim` JSON 中，否则无法表达多个文件、更正关系、公开副本和对象一致性。

公开副本是另一条 `Attachment`，通过 `source_attachment` 指向私有原件，受众为 public。私有原件本身永远不会通过切换布尔值变成公开对象。

### 2. 附件采用不可变对象与显式状态，不承诺对象存储 WORM

数据库服务禁止覆盖已提交对象 key 和内容元数据；更正上传新对象并建立 `supersedes` 关系。第一版依靠应用层、随机 key、SHA-256、一致性审计和私有 bucket 保证完整性，不要求 OCI Object Lock 或新的基础设施能力。

替代方案是在 bucket 启用 WORM，但这会显著增加环境配置和撤回/保留策略复杂度，且当前真实需求尚不足以证明必要。

### 3. 第一版文件策略按风险最小集合固定

允许 PDF、JPEG、PNG、WebP、CSV。图片原件保留字节，不执行头像裁切或只存 WebP；可以复用安全图片解码检查，但原件哈希必须对应实际保留字节。PDF 只验证真实类型、结构可读边界和大小，不执行脚本或渲染；CSV 只作为下载原件保存，不在浏览器内联呈现。

初始限额在实施中设为集中配置并写入测试：建议单文件 10 MiB、每次最多 10 个、总计 30 MiB。若仓库已有更严格的统一配置则复用更严格值。所有下载使用安全 `Content-Disposition`，私有 PDF/CSV 不直接嵌入公开页面。

不接受 SVG、HTML、压缩包、可执行文件、XLSX 或带宏文档。XLSX 等出现真实需求后再增加解析和安全策略。

### 4. 上传编排由领域服务负责，view 保持轻量

文件先流式处理到受控临时对象或内存/临时文件，通过验证后写入不可变 key；领域服务在数据库事务中创建报销、附件元数据和业务关联。若对象写入后事务失败，通过显式补偿删除尚未成为权威证据的对象。已提交对象的删除必须走受限 gateway，不能复用头像的 `delete_current()`。

数据库事务无法与对象存储形成分布式原子事务，因此采用“先安全写对象、再提交引用、失败补偿、后台一致性审计”的既有模式。附件批次服务自身必须使用数据库原子事务包住 `Attachment` 与业务关联创建，确保独立公开发布和更正入口在关联失败时也会回滚附件元数据；调用方外层事务继续覆盖服务返回后的事件写入或最终提交失败。两层补偿均按本次调用实际写入的不可变对象 key 删除，不能在尚未回滚的事务中用附件记录是否可见来判断。替代方案是先写数据库再异步上传，但会允许报销进入缺失凭证状态，不适合第一版闭环。

### 5. 附件权限由业务关联决定

私有支出凭证允许申请人及通过 `AuthorizationService` 获得 `finance.review`、`finance.pay` 或 `finance.view_private` 的成员按其操作需要读取；付款凭证至少允许申请人和财务私有查看者读取。具体页面入口仍传入 `ExpenseClaim` 上下文，不能只做全局权限判断。

公开副本只允许具备独立 `finance.publish_public_attachments` 权限的成员显式发布，并且仅在关联公开报销时通过独立受控路由提供。`finance.review`、`finance.pay` 和 `finance.view_private` 均不隐含公开发布能力。响应不暴露 object key；日志避免原始文件名和私密内容。Admin 只读展示元数据和状态，不提供绕过领域服务的编辑/删除。

### 6. 付款执行使用窄协议和不可变结果记录

新增 `PaymentExecution` 记录报销、后端类型、状态、付款日期、付款方式、付款人、备注、外部系统/对象 ID、同步状态、经过白名单过滤的结果快照和时间。成功执行后创建 `FinanceTransaction`，并通过关联或稳定 ID 把两者固定在同一事实链中。

`FinancePaymentBackend` 只接收经过本地授权和状态校验的付款请求，返回规范化结果；默认 `LiveOSManualPaymentBackend` 验证“财务人员已在线下付款”的确认数据，不调用外部服务。后端注册表只登记真实存在的实现，未知配置失败关闭。

不抽象报销提交、审核和公开审计，因为它们是 Live OS 永久拥有的制度事实；本次只抽象第一个具有真实替换价值的执行点。也不使用包含所有财务功能的 `FinanceBackend` 大接口，避免未来替换付款时被迫同时替换审核或会计。

### 7. 状态变化仍由 `core.finance_services` 编排

`mark_expense_claim_paid()` 扩展为接收付款表单和凭证，在同一领域事务中协调后端、`PaymentExecution`、附件关联、`ExpenseClaim.status`、`FinanceTransaction`、公开 `Event` 和 `SystemEvent`。所有权威状态变化函数继续保留 docstring，view 只解析表单和处理消息。

外部后端未来若需要长时间异步执行，可新增 pending/succeeded/failed 状态与回调服务；第一版内置人工后端同步完成，不提前引入任务队列。

### 8. 公开资料从结构化白名单投影

公开页只从报销、审核、付款执行的明确字段和 public `Attachment` 投影，不渲染原始后端快照或私有附件字段。收款方使用现有 `vendor` 作为公开名称；若未来需要法定名称与公开名称分离，再新增明确字段和迁移，不在本次猜测。

## Risks / Trade-offs

- [保留私有原件会积累存储成本] → 配置上传限额、按 world 审计容量；已进入证据链的文件不自动删除。
- [恶意 PDF 可能利用客户端阅读器] → 只允许下载、不在服务端执行或公开内联；使用安全响应头，后续按真实风险增加扫描服务。
- [CSV 可能包含公式注入内容] → 第一版不解析、不转换为 HTML，也不自动导入表格；下载时保持非内联处置。
- [对象存储与数据库无法原子提交] → 失败补偿、不可预测 key、提交后不可删除规则和一致性命令共同降低孤儿或缺失风险。
- [公开副本仍可能人工脱敏不彻底] → 发布动作要求独立权限、明确确认和审计；第一版不声称自动识别所有隐私信息。
- [后端抽象可能早于第二个实现] → 接口仅覆盖付款这一真实替换点，内置实现仍是完整默认路径，不建立第三方占位类。
- [已有报销没有附件] → 迁移允许历史记录保留；新提交和新付款从部署后开始强制凭证，不伪造旧记录。

## Migration Plan

1. 新增附件、报销附件关联和付款执行模型；迁移只创建新表或可空关联，不改写既有财务流水。
2. 部署代码但保持默认 `LiveOSManualPaymentBackend`；启动检查验证 Storage 和后端注册表。
3. 从新提交开始要求支出凭证，从新付款开始要求付款凭证；历史报销在 UI 标记为“旧记录，无结构化附件”，仍可查看原有事实。
4. 更新 workspace、observer 和只读 Admin，随后应用 world 数据库迁移并重启 real/simulation runtime。
5. 在隔离测试数据库中自动创建申请人、审核人、付款人和公开发布人四名虚拟成员，授予相互独立的测试职责并完成一笔 100 元报销的提交、审核、付款和公开副本闭环；另对 `simulation0001` 执行 runtime 清理 dry-run，不向开发数据库写入为了测试而伪造的财务业务记录。

回滚代码时保留新表和对象，不执行破坏性逆迁移；旧代码会忽略新记录。若新上传入口出现严重问题，关闭入口并继续保留已提交证据，修复后恢复。
