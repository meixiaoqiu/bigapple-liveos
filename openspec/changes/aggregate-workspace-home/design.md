## Context

参见 `proposal.md` 的动机说明。当前 `workspace/context.py` 直接汇集任务、申诉、积分、事件和资源信息，`workspace/work_item_context.py` 已对部分治理与采购待办进行聚合，但其输出按处理类型拆分，首页仍由多个业务模块主导。

本次需要跨越 context、聚合构建器、模板和测试，但不改变数据库、领域 service、API 或权限事实。迁移期必须允许新旧展示重复。

## Goals / Non-Goals

**Goals:**

- 建立小而稳定的页面投影格式，表达事项身份、状态、责任、处理方、动作和更新时间。
- 复用现有查询与权限判断，把首页新增区域保持为只读组合层。
- 让新区域位于旧模块之前，同时以测试保护全部旧模块及操作入口。
- 产出后续逐项确认旧模块所需的清单。

**Non-Goals:**

- 不把页面投影提升为跨领域持久化模型或 service 门面。
- 不为了填满投影字段而新增责任人字段或改变业务状态。
- 不在本次处理旧模块删除、业务专页重构或新路由设计。

## Decisions

### 1. 扩展现有聚合模块，而非新增通用事务内核

在 Workspace 层扩展现有工作项构建器，使其输出统一的展示字典，并由 `workspace_context` 注入模板。该层只读取领域数据，不承接状态变化。

未采用建立 `Transaction` 模型或跨领域 `TransactionEngine` 的方案，因为本次没有新的权威状态需求，而且持久化统一模型会引入同步、迁移和状态一致性问题。

### 2. 按成员行动关系分组，而非统一业务状态

聚合结果分为“需要我处理”“等待他人”和“最近结束”。各领域原始状态保留为展示值，不映射为可驱动业务的统一状态机。

未采用把所有领域状态压缩成 `pending/in_progress/ended` 的方案，因为这会丢失业务语义，并容易让页面层成为新的规则来源。

### 3. 缺失责任信息时显式降级

投影优先显示现有明确责任成员；只能确定处理角色时显示责任角色；两者都不能可靠确定时显示“暂未明确”。不因展示需要修改模型或推断个人。

未采用自动指定默认责任人的方案，因为这会改变权威责任事实，超出首页改版范围。

### 4. 保留旧模块作为迁移期对照基线

模板仅插入新聚合区域并调整旧内容位置。旧模块内部 HTML、表单 action、链接和权限条件原则上不改；测试对关键模块标题和操作入口建立存在性断言。

未采用立即清理重复内容的方案，因为使用者要求在完成本次任务后逐个确认、逐个删除。

上述保留规则是聚合初次上线的迁移基线，不是永久禁止清理。初次验收后，使用者可通过后续独立 change 逐项确认删除或迁移；对应 change 负责定义替代入口、服务器端与契约清理及回归验证，清单同步记录当前状态。

### 5. 开放任务继续作为机会展示

未领取任务不代表当前成员已经承担责任，因此不进入个人事务投影。后续经逐项确认后，独立任务中心承担发现与领取入口。

### 6. 数据库先筛选真实待办，再进行展示排序

治理提案通过审批决定 `EXISTS` 子查询，在数据库中筛选当前成员仍可填补审批角色的记录；待执行提案独立按 `resolved_at` 排序。采购验收通过采纳提案存在性及执行状态 `EXISTS` 子查询筛选，付款则直接使用领域状态条件。查询返回的都是已经符合处理条件的事项，不对尚未判断的候选设置固定窗口。

旧待办模块与新事务区域共享筛选后的真实待办集合。每个来源在数据库完成资格筛选和原有排序后只加载前 20 条，足以参与最终全局前 20 条合并；旧模块的完整数量由独立数据库计数保留，不因展示切片而截断。采购验收只使用同一报价按提交时间排序后的最新采纳提案状态，避免历史已执行提案覆盖更新但尚未执行的提案。

未采用“先取最新 N 条候选再逐项判断”，因为任意固定 N 都可能静默漏掉更早但仍有效的待办。也未采用无上限 Python 扫描，因为权限判断会随历史数据线性增长。

## Risks / Trade-offs

- [迁移期同一事项重复展示] → 明确标注新区域为聚合视图，并在交付清单中记录重叠，后续逐项确认清理。
- [不同领域责任字段不一致] → 采用明确降级规则，不为追求视觉一致性伪造责任信息。
- [聚合查询增加首页成本] → 复用已加载数据或使用有界查询与关联预取，并在实现评审中检查明显的逐项查询。
- [模板重排误伤旧操作] → 不重写旧模块内部结构，以页面回归测试验证标题、表单和链接仍存在。
- [投影被误用为权限判断] → 所有可执行性继续由现有权限函数和领域规则计算，模板只消费结果。

## Migration Plan

1. 先增加聚合投影及单元测试，不改变模板现有区域。
2. 在首页旧模块之前插入新事务区域。
3. 运行 Workspace 回归、权限故障检查、Tailwind 构建和基础项目检查。
4. 同步 Workspace 产品说明，并输出旧模块待确认清单。
5. 若出现回归，可移除新区域及其 context 接入；由于没有 schema 或权威数据变化，不需要数据回滚。
