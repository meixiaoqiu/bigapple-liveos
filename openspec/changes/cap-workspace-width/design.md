## Context

参见 `proposal.md`。当前 Workspace 主体使用 `max-w-7xl`，并通过 `sm`、`md`、`lg`、`xl` 视口断点把多个区域切成横向布局。仅把外层限制到 480px 会导致桌面视口仍触发这些规则，在狭窄容器中挤出多列，因此外壳与内部断点必须同时收敛。

## Goals / Non-Goals

**Goals:**

- 为 Workspace 首页建立宽度唯一、可测试的 480px 竖版外壳。
- 让公共页头在 Workspace 页面内与主体对齐，同时不影响其在其他页面的布局。
- 保持现有模板内容和 Django 条件原样存在，为后续局部替换提供稳定基线。

**Non-Goals:**

- 不在本次抽取完整 Workspace base template。
- 不把设计稿中的 header、快捷入口、tab 或底部导航直接复制到产品代码。
- 不改变子页面宽度；先验证首页外壳，再逐步决定是否扩展到 Workspace 子页面。

## Decisions

### 1. 使用单一白色画布承载 480px 首页

首页页头和主体放入同一个 `w-full max-w-[480px] min-h-screen mx-auto bg-white` 外壳，`body` 保持灰色背景。小于 480px 时白色画布自然占满可用宽度，大于 480px 时画布停止扩张并居中，两侧灰色背景形成清楚但不依赖额外边框或阴影的页面界限。

备选方案是 600px。该宽度更接近平板内容栏，会削弱设计稿的竖版应用比例，因此不采用。备选的 448px 和 512px 都是常见预设，但 480px 更接近主流大屏手机与桌面竖版壳之间的折中。

### 2. 只在 Workspace 调用处约束公共页头

不修改 `runtime_header.html` 的全局宽度，而是把 Workspace 首页包含的 partial 放入同一个局部应用画布。这样不会意外把观察台、错误页或其他运行时页面一并变窄。

备选方案是直接修改公共 partial。它会扩大本次改造范围并改变非 Workspace 页面，因此不采用。

### 3. 首页主要布局取消视口驱动的多列断点

导航分组、事务分组、待处理事项和核心状态改为固定单列。外部视口宽度不再决定 480px 容器内部的列数。

备选方案是保留现有断点。由于媒体查询观察的是视口而非容器，它会在桌面端把窄容器内容强行压成三列或四列，违反统一竖版布局，因此不采用。

## Risks / Trade-offs

- [现有模块在单列中使页面变长] → 本阶段接受纵向增长；后续逐模块改为设计稿的紧凑卡片和 tab，而不是在本次删除内容。
- [白色画布在窄屏上没有可见外边界] → 这是预期行为；窄屏由视口本身定义边界，宽屏才由两侧灰色背景显出画布范围。
- [极窄设备仍需要自然换行] → 保留 `w-full` 与现有内部换行能力，不钉死最小宽度。

## Migration Plan

模板和 Tailwind CSS 一同发布，无数据迁移。回滚时恢复页头与主体的独立容器即可，不涉及业务状态。
