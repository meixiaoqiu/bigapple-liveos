## Purpose

建立以用户可见业务事件为唯一锚点的统一反馈与处置流程，覆盖纠错、意见、投诉、举报、复核和风险，并以明确的数据、权限和身份展示边界替代旧申诉模型。

## ADDED Requirements

### Requirement: 每条反馈必须关联可见业务事件
系统 MUST 要求每条事件反馈关联一个现有 `Event`，并在创建时确认提交成员有权查看该事件；不得创建无事件反馈，也不得把仅供审计的 `SystemEvent` 直接作为反馈目标。

#### Scenario: 成员从可见事件详情提交反馈
- **WHEN** 已登录成员在其有权查看的事件详情提交有效反馈
- **THEN** 系统创建一条固定关联该事件的反馈，且提交内容不能替换关联事件

#### Scenario: 成员尝试反馈不可见事件
- **WHEN** 成员提交其无权查看或不存在的事件标识
- **THEN** 系统返回 404 且不泄露事件或反馈信息

### Requirement: 统一反馈类型具有明确语义
系统 SHALL 支持 `correction`、`opinion`、`complaint`、`report`、`review` 和 `risk` 六种反馈类型，并分别展示为纠错、意见、投诉、举报、复核和风险。

#### Scenario: 成员选择反馈类型
- **WHEN** 成员提交反馈
- **THEN** 系统只接受六种已定义类型，并保存事实陈述、期望结果和证据引用

#### Scenario: 成员报告尚未发生的风险
- **WHEN** 成员认为事件反映了可能造成未来损害的危险
- **THEN** 系统允许其选择风险类型，并按风险事实和预防措施进行核实与回应

### Requirement: 反馈使用统一公开核实流程
系统 MUST 使用已提交、核实中、等待回应、已形成结论、已结束和已撤回状态表达反馈生命周期；创建、开始核实、请求回应、形成结论、结束和撤回必须通过领域服务执行并写入统一事件账本。

#### Scenario: 责任人处理反馈
- **WHEN** 有权成员分配核实责任人、核实事实、请求相关方回应或公布结论
- **THEN** 系统验证合法状态转换，保存明确责任成员、回应和依据，并追加对应审计事件

#### Scenario: 普通成员撤回未处理反馈
- **WHEN** 提交人撤回仍处于已提交状态的反馈
- **THEN** 系统将其标记为已撤回并保留原始记录

### Requirement: 提交人自行选择身份展示范围
系统 MUST 默认公开提交人身份，并允许提交人选择 `public`、`parties_and_handlers` 或 `handlers_only`；选择非公开范围时 MUST 填写限制身份展示理由。系统内部和核实责任人始终能确认真实提交人。

#### Scenario: 提交人采用默认公开身份
- **WHEN** 提交人没有选择限制身份展示
- **THEN** 反馈页面公开显示其身份

#### Scenario: 提交人限制身份展示
- **WHEN** 提交人选择非公开身份范围并填写理由
- **THEN** 系统按其选择限制公开身份，向核实责任人显示真实身份，并且不默认公开可能暴露身份的理由

### Requirement: 第三方隐私不由提交人决定
系统 MUST 独立保护第三方个人信息、凭据、医疗信息和其他依法或依规则受保护内容；提交人对自己身份的选择不得授权公开他人受保护信息。

#### Scenario: 反馈包含第三方受保护信息
- **WHEN** 反馈内容或证据包含第三方受保护信息
- **THEN** 系统仅向提交人、明确相关方和核实处理人展示成员提交的原始陈述、期望结果、证据与回应；公开页面只公布经处理人核实后形成的结论、依据和责任人

### Requirement: 相关方可以正式回应
系统 MUST 向反馈指向的相关方展示事实主张并提供正式回应机会；身份展示限制不得阻止相关方针对事实和证据回应。

#### Scenario: 相关方提交回应
- **WHEN** 核实责任人请求相关方回应
- **THEN** 系统保存回应人、回应内容和时间，并在允许的公开范围公布

### Requirement: 反馈结论使用统一结果分类
系统 MUST 支持 `confirmed`、`partly_confirmed`、`not_confirmed`、`inconclusive` 和 `not_applicable` 结论，并公布结论、依据和责任人；意见可使用不适用，证据不足时必须使用无法核实而非强行二元判断。

#### Scenario: 证据不足以判断事实
- **WHEN** 核实完成但证据不能支持属实或不属实
- **THEN** 系统记录无法核实，并公布缺失证据和判断依据

### Requirement: 反馈结论不覆盖原事件
系统 MUST 保持原事件不可由反馈流程覆盖；需要纠正权威业务状态时，处理者必须使用对应业务领域动作，并可把新产生的 `Event` 记录为反馈的 `resolution_event`。

#### Scenario: 纠错反馈成立
- **WHEN** 处理者确认反馈成立且对应领域完成正式纠正
- **THEN** 原事件保持不变，反馈结论链接新的结果事件

### Requirement: 事件详情承载反馈入口和上下文
系统 SHALL 在成员有权查看的事件详情提供反馈入口，并向提交人和有权处理者展示其可见的关联反馈；Workspace 首页不得提供脱离事件的反馈创建表单。

#### Scenario: 登录成员打开公开事件详情
- **WHEN** 已登录成员打开公开事件详情
- **THEN** 页面显示固定关联该事件的反馈表单和该成员可见的反馈记录

#### Scenario: 未登录访客打开公开事件详情
- **WHEN** 未登录访客打开公开事件详情
- **THEN** 页面继续显示公开事件，但不允许提交或查看非公开反馈

### Requirement: Workspace 投影反馈事务而不复制创建入口
系统 MUST 将提交人等待处理、处理人需要行动和最近结束的反馈投影到“我的事务”，并从 Workspace 首页删除旧申诉状态和提交模块。

#### Scenario: 成员存在进行中反馈
- **WHEN** 当前成员是反馈提交人或明确处理人
- **THEN** “我的事务”按责任关系展示该反馈并链接事件详情或反馈详情

#### Scenario: 反馈相关方或处理人需要行动
- **WHEN** 当前成员是等待回应的明确相关方，或是核实、形成结论、结束阶段的明确处理人
- **THEN** 该反馈进入“需要我处理”并显示与当前状态一致的动作；其他参与关系进入“等待他人”

### Requirement: 旧申诉契约完全移除
系统 MUST 删除 `Dispute` 模型及 `/disputes` 契约，不保留旧名称、旧字段、旧 API 别名或旧数据兼容层，并以 `EventFeedback` 和 `/event-feedbacks` 替代。

#### Scenario: 客户端使用新反馈 API
- **WHEN** 已授权客户端针对可见事件提交事件反馈
- **THEN** 响应遵循 event-feedback schema，且旧 `/disputes` 路径不存在
