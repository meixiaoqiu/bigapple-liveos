## Context

当前任务创建、预算锁定和发布分别由 `workspace.task_views`、`workspace.credit_views`、`core.tasks.authoring` 与 `core.credit_services` 承担。任务只有生成 `task_id` 后才能成为 `CreditTransaction.related_task`，而发布服务要求已有足额预算，因此页面迫使管理员在两个入口之间往返。

积分账本只能追加；发布判断必须使用任务关联的剩余锁定预算；运行时数据写入必须留在当前 world 数据库。参见 `proposal.md` 与 `specs/task-funding-publishing/spec.md`。

## Goals / Non-Goals

**Goals:**

- 用领域编排服务收敛“计算缺口、锁定缺口、发布任务”的一致性边界。
- 让创建页在一次提交内完成创建与发布，或得到明确的草稿结果。
- 复用现有 `CreditTransaction`、任务状态和 `SystemEvent`，保持账本与审计语义不变。
- 让既有草稿的发布按钮同样自动补足预算缺口。

**Non-Goals:**

- 不允许组合操作自动调用积分发行。
- 不将积分预算页改造成第二个任务编辑器。
- 不改变奖励公式、验收发放、驳回保留预算或未用预算退回规则。
- 不新增数据库字段或第三方依赖。

## Decisions

### 1. 在任务领域增加组合发布服务

增加一个位于 `core.tasks` 领域包中的服务，接收任务、发布责任人和锁定责任人，完成以下逻辑：

1. 锁定并重新读取草稿任务；
2. 计算 `expected_reward = base_points × role_coefficient`；
3. 读取任务当前剩余锁定预算；
4. 计算 `shortfall = max(expected_reward - locked, 0)`；
5. 若 `shortfall > 0`，从发行池追加一条与任务关联的 `LOCK` 交易；
6. 调用或复用发布状态转换并追加任务事件。

该服务使用与当前 world 相同的数据库连接和单一事务。事务内必须重新校验发行池余额与任务状态，不能依赖页面渲染时的快照。

未采用“由 view 顺序调用锁定服务和发布服务”的方案，因为两个各自正确的调用之间仍可能留下部分完成状态，也会把权威编排放在 view 中。

未采用“让 `publish_task()` 永远自动锁预算”的方案，因为底层发布服务当前表达的是状态转换与预算前置条件；将资金副作用隐式塞入所有调用者会扩大行为变化。使用命名明确的组合服务可保留低层原语，并让调用者显式选择自动资金路径。

### 2. 创建并发布采用两阶段结果语义

创建页的“锁定预算并发布”先创建合法草稿，再尝试组合发布：

- 余额充足：创建、锁定和发布作为一个成功事务提交；
- 余额不足：不写入部分 `LOCK`，但提交新建草稿，并返回结构化缺口信息；
- 其他领域错误：不提交本次创建产生的权威写入。

为清晰表达“余额不足但草稿已保存”不是异常半状态，创建编排应返回显式结果对象或状态值，而不是依赖解析错误消息。余额检查与实际锁定仍必须在加锁事务中完成，避免并发超额使用发行池。

未采用“余额不足时整次回滚、不保存任何任务”的方案，因为用户已经完成任务定义，丢弃输入会增加重复劳动，且不利于后续补充发行或调整奖励。

### 3. 自动锁定预算缺口而非总额

既有草稿可能已通过维护页面锁定部分预算。组合服务只锁定 `预计奖励 - 当前锁定预算`，避免重复锁定。若当前预算已经足额，则直接发布；超额锁定预算保持现状，后续仍可通过既有退回流程处理。

未采用“每次发布固定再锁完整奖励”的方案，因为它会在重试或已有预算时重复占用公共池。

### 4. 发行保持独立且不嵌入组合事务

任务页可以展示发行池余额、预计奖励和缺口，并链接积分预算页，但不得在同一按钮中创建 `ISSUANCE` 交易。发行改变积分总供应，必须保持独立原因、责任人与幂等键。

未采用“余额不足自动发行差额”的方案，因为它把日常任务发布升级为货币供应操作，模糊治理授权与审计意图。

### 5. 页面动作使用显式 intent

创建表单提交显式 `intent=save_draft` 或 `intent=fund_and_publish`。既有草稿的“发布”按钮改为调用组合发布路径，并在按钮附近展示预计奖励、已锁预算和预计补锁额。积分预算页保留手工维护功能，但任务选择优先使用可识别的草稿列表，而不是要求记忆或复制 ID；此项属于同一体验优化，但不改变账本规则。

### 6. 权限在入口和服务边界同时保持明确

workspace 入口继续要求当前 world 的完整成员身份与现有管理员/治理授权。组合服务不得通过调用者提供的成员编号选择责任人，必须使用 session 推导的当前成员生成实名 actor。若任务管理与预算管理权限未来拆分，组合操作必须要求两者同时满足并失败关闭。

## Risks / Trade-offs

- [余额展示可能在提交前过期] → 展示值仅作提示，事务内重新加锁校验并返回最新缺口。
- [创建成功但余额不足容易被误解为发布失败] → 使用明确的提示和草稿状态卡片，说明任务已保存、未锁定、未发布及下一步。
- [复用多个已有原子服务可能形成嵌套事务] → 由组合服务建立外层事务，底层服务保持可组合，并为回滚行为增加集成测试。
- [并发发布多个任务竞争发行池] → 对相关系统账户/交易决策使用现有并发保护，测试总锁定额不得超过发行池余额。
- [手工预算页仍允许错误输入任务 ID] → 正常路径不再依赖它；实施时优先提供草稿选择控件，保留服务端对象校验。
- [事件顺序发生变化] → 明确验证成功路径先形成任务创建事实，再形成预算锁定和任务发布事实，失败路径不产生误导性发布事件。

## Migration Plan

1. 先增加组合服务及成功、余额不足、部分预算、并发与回滚测试。
2. 调整任务创建页的两个 intent，并把既有草稿发布切换到组合服务。
3. 增加预算摘要和缺口提示，保留原有预算维护入口。
4. 同步任务运营流程、workspace 产品文档、架构边界和验证说明。
5. 使用隔离测试设置运行任务、积分、workspace、API 与 world 路由相关测试。

回滚时可把页面恢复为原有分步入口并停止调用组合服务；新增服务不改变数据库结构，既有追加式流水和已发布任务无需数据回滚。
