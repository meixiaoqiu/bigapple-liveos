## Why

当前有积分奖励的任务必须经过“发行积分、创建任务、复制任务 ID、返回预算页锁定、再返回任务页发布”的多次往返，用户被迫手工协调本应由系统完成的任务与预算关系。需要在保留追加式积分账本、预算先行和实名责任边界的前提下，把正常任务发布收敛为一次明确且原子的业务操作。

## What Changes

- 在任务创建页提供“保存草稿”和“锁定预算并发布”两个明确动作。
- 系统根据任务的 `base_points` 与 `role_coefficient` 自动计算发布所需预算，不要求用户复制任务 ID 或手工填写正常发布所需的锁定金额。
- “锁定预算并发布”在同一事务中创建任务、锁定准确预算并开放领取；任一步失败时不得留下部分完成状态。
- 发行池余额不足时保留可继续处理的草稿，明确展示当前余额、所需预算和缺口，不自动发行积分。
- 积分发行继续作为独立的高影响治理动作；积分预算页继续承接补锁、追加和退回等异常或维护场景。
- 保留现有任务发布预算校验、追加式 `CreditTransaction` 流水、任务生命周期事件和 world 数据边界。

### 目标

- 将有积分任务的正常发布缩短为一次表单提交。
- 消除任务 ID 的人工复制和正常锁定金额的人工计算。
- 保证任务状态、预算流水和事件记录一致且可审计。

### 非目标

- 不把积分发行合并为任务发布的隐式步骤。
- 不改变积分奖励计算公式、验收发放规则或积分总供应治理规则。
- 不移除积分预算页的手工补锁、追加预算和退回能力。
- 不新增角色，也不放宽任务管理或积分管理权限。

### 权限影响

- 组合发布操作仅对同时满足现有任务管理和预算锁定权限的主体开放；不得以 Django `is_staff`、`is_superuser` 或硬编码成员身份替代业务授权。
- 发行积分仍使用独立权限与显式确认，不因任务发布而自动发生。

### 数据影响

- 不要求新增权威模型或修改既有账本结构。
- 成功组合发布会追加既有 `LOCK` 类型积分交易及任务生命周期事件。
- 失败操作必须回滚当次创建、锁定和发布写入；余额不足时若产品选择保留草稿，该草稿创建是明确结果而非半完成事务。

### 公开契约影响

- 当前预计不修改公开 API schema 或 payload；变更集中在 workspace 页面与领域服务编排。
- 若实施中需要新增公开端点或字段，必须先更新 sibling 仓库中的 technical contracts。

## Capabilities

### New Capabilities

- `task-funding-publishing`: 定义任务草稿保存、自动预算计算、原子锁定并发布、余额不足处理及发行边界。

### Modified Capabilities

无。

## Impact

- 主要影响 `workspace/task_views.py`、任务管理模板、`core.tasks.authoring` 与 `core.credit_services` 的组合编排及相关测试。
- 需要同步任务运营流程、成员工作台、架构边界与开发验证文档。
- 不新增第三方依赖，不改变 OpenFGA 模型，不改变数据库表结构。
